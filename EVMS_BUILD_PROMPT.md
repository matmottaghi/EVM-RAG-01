# Master Prompt — Build EVMS Intelligence Web Application

You are a senior Python software architect and AI engineer.

Build a complete, production-structured MVP web application named **EVMS Intelligence** for conversational analysis of Earned Value Management System data stored in Microsoft SQL Server.

The application must use Python as the primary programming language and Django as the web framework.

Do not replace Django with Flask, FastAPI-only, Node.js, React-only, or another backend framework.

Use LangChain for LLM integration and LangGraph for orchestration and human-in-the-loop workflow control.

---

## 1. Application Goal

The user asks a natural-language question about EVMS data.

The system must:

1. Receive the user's question.
2. Send the question and semantic database schema to the LLM.
3. Generate a read-only SQL query.
4. Validate the SQL.
5. Execute the SQL against Microsoft SQL Server.
6. Convert the result to a pandas DataFrame.
7. Show the retrieved data to the user in the right panel.
8. Pause the LangGraph workflow.
9. Display **Approve Data** and **Reject Data** buttons.
10. Never send the dataset to the analysis model before explicit user approval.
11. If approved, resume the LangGraph workflow.
12. Send only the approved dataset to the LLM for analysis.
13. Return a concise data-grounded EVMS analysis to the chat panel.
14. Send the approved data and analytical context to a chart-planning step.
15. Generate a validated chart specification.
16. Render an interactive chart in the left panel.

If the user rejects the dataset, do not analyze it. Allow a correction message and regenerate the query.

## 10. Critical Safety Rule

This rule is mandatory and must be enforced in code, not only in prompts:

```text
UNCONFIRMED DATA MUST NEVER BE SENT TO THE ANALYSIS LLM.
```

Both the analysis node and chart-planning node must verify:

```python
confirmation_status == "approved"
```

If not approved, raise a controlled workflow error.

## 11. SQL Generation Prompt

Create a system prompt telling the LLM:

- act as a SQL Server query planner
- use only provided views and columns
- generate only SELECT statements
- never modify database data
- prefer aggregation when possible
- use aliases understandable by business users
- return structured JSON

Output schema:

```json
{
  "sql": "SELECT ...",
  "reason": "Short explanation"
}
```

## 12. SQL Validation

Create a deterministic validator before SQL execution.

Reject SQL containing any of the following tokens:

```text
INSERT
UPDATE
DELETE
DROP
ALTER
CREATE
EXEC
EXECUTE
MERGE
TRUNCATE
GRANT
REVOKE
```

Also reject:

- multiple statements
- unknown tables
- unknown views
- cross-database access
- system tables

Only allow configured EVMS views.

Prefer querying semantic views instead of raw transactional tables.

## 17. Reject Endpoint

When rejected:

- set confirmation status to rejected
- do not call the analysis LLM
- do not generate a chart
- return a response asking the user to clarify the problem with the retrieved data

The next user message may be used as correction context for regenerating SQL.

## 28. Final Architectural Constraint

The application must enforce this exact business process:

```text
Natural Language Prompt
        ↓
LLM SQL Generation
        ↓
SQL Validation
        ↓
SQL Server Query
        ↓
Display Dataset to User
        ↓
Human Approval / Rejection
        ↓
Only if Approved
        ↓
LLM Data Analysis
        ↓
LLM Chart Specification
        ↓
Validated Interactive Chart
```

Do not bypass the confirmation stage.

Do not send SQL results to the analysis model before confirmation.

Do not allow the LLM to execute arbitrary Python code.

Prioritize simplicity, maintainability, auditability, and clear separation between data retrieval, confirmation, analysis, and visualization.
